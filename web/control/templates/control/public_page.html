The execution model

From a declared obligation to inspectable evidence.

1. Select an approved scope

A profile identifies the registered adapter, operation, expected result, required capabilities and bounds. Missing required capabilities stay UNSUPPORTED. The public demo is recorded playback, entirely separate from live execution.

2. Run through private supervision

The web request queues a durable job. A private executor reauthorizes the project/target and invokes the existing CLI through fixed arguments. On QNX, the independent supervisor delegates every potentially blocking service operation to an owned worker.

3. Inspect each obligation

Native pending, trigger, result, state, fresh-client health and cleanup observations remain distinct. The existing deterministic evaluator produces PASS, FAIL, ERROR, UNSUPPORTED and NOT_RUN. A timeout configuration is not a measured expiry, and a restart is not original-instance health.

4. Replay an identified correction

Saved inputs retain original manifests, fixture controls and hashes. A candidate must be operator-approved and explicitly selected. Changing fixture mode is an incomparable contrast, not a source-fix proof.

Supported boundary

Security and limitations

Projects and evidence are scoped to current organization/project membership. Administrators use locally provisioned usernames and passwords; MFA is deferred for this hackathon release. Developer and jury access uses scoped access codes. Queued work is reauthorized before dispatch. A browser cannot choose arbitrary commands, SSH hosts or executable paths.

The private lab is not an anonymous execution sandbox. Public playback contains only already published fixture evidence. Customer connections require dedicated runner/route approval. Arbitrary external lifecycle testing is UNSUPPORTED without implemented, natively qualified adapters and observers.

The QNX engine qualifies recorded conditions on two fixture protocols. It does not claim exhaustive concurrency, absence of memory leaks, hardware worst-case timing, safety certification or universal driver support.

Evidence hashes detect changes; they are not malicious-root attestation. Unknown ownership, transport uncertainty and missing evidence never become PASS. AI is supplementary, opt-in and cannot alter results, run tools, apply patches or restart services.

Data handling

Privacy and retention

Only administrators have locally provisioned username/password accounts. Existing encrypted MFA records are retained for future reactivation. Developer access uses keyed code verifiers and revocable session/security records; no email or developer password account is required. Organizations store explicit grants, project configuration and authorized test evidence. Private SSH/SDK credentials stay outside browser responses and evidence downloads.

Project evidence is private to its authorized members. The public demo uses the separately identified, already published QNX fixture cases. Your activity is not silently added to that demo.

AI processing requires project enablement and explicit request consent. Selected evidence and any separately consented source can leave the server for the configured provider. Provider/model, budgets and uncertainty must be disclosed. Disabled AI leaves deterministic testing available.

Organization evidence retention defaults to30 days, subject to explicit holds. Administrators can revoke codes or browser sessions immediately. Minimal grant, consent and security/audit identity records are retained to preserve evidence provenance; source and AI content have their separate30-day expiry. Administrator credential recovery is a protected local procedure, never email. Backups follow the documented operational retention.

For operator questions, use the repository contact link. Production operational settings and provider details must be reviewed before enabling their integrations.

Authorized engineering use

Terms and scope

Test only systems and source you are authorized to use. A workspace or approved fixture runner does not grant rights to another party's QNX runtime, SDK, service or credentials. Obtain applicable QNX licensing separately.

Results apply to the recorded contract, inputs, build and environment. Treat source suggestions and AI explanations as untrusted engineering assistance requiring review. They are not authoritative test verdicts or permission to deploy changes.

Do not upload passwords, API keys, private SSH keys, SDK/license material or proprietary runtime images. Only supported evidence/manifests and authorized source should be provided. No public unrestricted execution endpoint is offered.

The original project code is MIT licensed. Third-party tooling and licensed QNX inputs retain their own terms. Operational access/quotas are controlled by project and platform administrators.
